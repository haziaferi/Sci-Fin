Budget — density held by the measure

The rule is no longer about panes. It is about what happens to an element when you stretch it. Progress.kt:45 builds the category bar as fillMaxWidth() with a fixed height(5.dp) and no maximum, so widening a column does not scale the bar — it changes the bar's aspect ratio without limit, until a proportion reads as a hairline.

The bar, stretched. Height 5dp throughout; only the width changes. Phone ≈ 62:1 is the shape it was designed as.
308px — phone, 62:1
434px — the measure, 87:1
971px — a single column at the current window, 194:1

All three encode the same 37%. The third is not a fuller bar, it is a longer one — and at 194:1 the eye reads a line, not a quantity. That is the density argument made visible, and it is why the column must stop growing.

The number is already in the build, and it is not 530. Controls.kt:137 defines measureCap as base × 0.55 × 52 — 52 characters, which is 458dp at the default text size. It is derived from §2.5's own ramp, not borrowed from another app, and it grows with the OS text setting: at XL it is 686dp. My earlier proposal of 530, taken from Actual Budget, is withdrawn — the build had a better-founded number all along. What is new is applying it to the column, not only to prose.

The rule, entirely in existing tokens: a column is one measure wide, never more. The content area holds as many columns as fit at N × M + (N−1) × gap. Extra width is left empty and the block centres. Nothing stretches, ever.

Why this fixes the threshold problem. With M = 458, two columns need 932 of content. The app's current window gives 995 — so the split is the default, not something you have to drag the window to reach. With the borrowed 530 it needed 1076, which the default window missed.

The bar's aspect ratio is constant in every row but the last. That is the whole point: the window changes how many columns there are, never how stretched an element is. Density is held by construction.

A defect this drawing exposes, in the build not the mockup. The aspect ratio is constant across window sizes, which is the whole aim — but not across text sizes. The measure grows with the text setting (458 at MD, 686 at XL) while Progress.kt:51 fixes the bar at height(5.dp), a bare literal that grows with nothing. Measured in frame 4: 132:1 at XL against 87:1 at MD. The people who most need large text get the most distorted bars. The fix follows from the same ramp: the bar height should be base × 0.3125 — 5dp at MD, 7.5dp at XL — which holds the aspect at 87:1 on both. It is also an instance of the known “no dp literals under ui/” rule that §2.5's scale pass already owes.

The one thing still open: the third column. At 1711 a third column of 458 fits with 305 to spare, which would cut the empty space from 779 to 305. Budget only has two sections, so a third column would have to hold something — Categories flowing into two columns, or Goals promoted out of Envelopes. That is a content decision, not a layout one, and it is not made here.
